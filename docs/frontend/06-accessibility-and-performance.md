# Accessibility & Performance

Source: Nova Enterprise Blueprint, **Volume 6, Part E2** (accessibility) and **Part E3** (low-connectivity performance budget). Both are restated below as concrete, testable criteria rather than the source prose, per the task brief — a checklist someone can actually run against a PR, not a paragraph to nod along to.

## Accessibility (Vol 6, E2) — WCAG 2.2 AA checklist

> "Every customer-facing and seller-facing surface targets WCAG 2.2 AA conformance: sufficient color contrast, full keyboard navigability on web, screen-reader-compatible markup and labeling, and touch-target sizing appropriate for the mid-tier Android devices common in the target market. Accessibility is verified through the automated and manual review process defined in Volume 3, Part J5, not treated as optional polish."

| Criterion                  | Concrete, testable check                                                                                                                                                                                                                                                                                                   | Current state                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Color contrast**         | Every text/background pairing sourced from `variables.css` meets **4.5:1** for body text, **3:1** for large text (≥18px/14px-bold) — WCAG 1.4.3. Run automated contrast checking (axe / Storybook's a11y addon) against every token pairing in `packages/design-system/src/tokens/colors.ts`, not just spot-checked pairs. | Not yet verified as a checklist item — the tokens themselves were corrected for brand accuracy this session, but a systematic contrast audit of every semantic pairing (e.g. `--color-foreground-muted` on `--color-surface` in both light and dark) hasn't been run.                                                                                                                                                                                |
| **Keyboard navigability**  | Every interactive element reachable via `Tab`, every custom component (`Dialog`, `Dropdown`, `Menu`, `Tabs`) implements the correct ARIA keyboard pattern (Escape closes a `Dialog`, arrow keys move within a `Menu`), and focus is never trapped or lost on route change.                                                 | Partial evidence: `ProductCard`'s focusable elements use `focus-visible:ring-2 focus-visible:ring-[color:var(--color-border-focus)]` — a real, token-correct focus ring. No systematic keyboard-nav test exists yet across the 34 design-system components.                                                                                                                                                                                          |
| **Screen-reader labeling** | Every icon-only button has an `aria-label`; every image has meaningful `alt` text (or `alt=""` if purely decorative); every form input has an associated `<label>` or `aria-label`; landmark regions (`<nav>`, `<main>`) are used correctly.                                                                               | Real evidence both ways: `navigation.searchAriaLabel` exists in the message catalog ("Search products") and a `skipToContent` key exists — genuine accessibility-aware i18n. But `NewsletterSection`'s email input uses `aria-label="Email"` hardcoded in English directly in the component rather than pulled from the message catalog — see [07-localization.md](07-localization.md) for why that's also a localization gap, not just an a11y one. |
| **Touch target sizing**    | Minimum **24×24 CSS px** (WCAG 2.5.8, the actual AA-level 2.2 requirement — not the stricter 44×44 AAA guideline, though meeting 44×44 where practical is still the better target for a mid-tier-Android, thumb-driven market).                                                                                            | The design system's `Button` component's real size scale: `xs` = 28px, `sm` = 36px, `md` (default) = 40px, `lg`/`xl` = 44–48px, `icon` = 40×40px. **Every size variant already clears the 24px AA minimum**; only `lg`/`xl` clear the stricter 44px guideline. Worth defaulting to `lg` rather than `md` specifically for primary mobile-web CTAs (add-to-cart, checkout continue), given the market this doc set keeps citing.                      |
| **Automated verification** | `@storybook/addon-a11y` runs against every component story.                                                                                                                                                                                                                                                                | Installed this session (`packages/ui/.storybook/main.ts`) — real, current, but Storybook itself is currently broken by an unresolved `@storybook/nextjs` + Next.js 15 webpack incompatibility (documented in the root README's Commands section), so the addon can't actually run yet. This is a real blocker on the "automated" half of Vol 3, J5's verification requirement, not a hypothetical one.                                               |

## Performance for low-connectivity conditions (Vol 6, E3)

> "...every surface is designed against an explicit performance budget: aggressive image optimization and lazy loading, optimistic UI updates for common actions... and graceful offline/degraded-connectivity states on mobile rather than blank screens or silent failures."

| Criterion                                  | Concrete, testable check                                                                                                                                                                                                                                                           | Current state                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Image optimization**                     | Every product/content image uses Next.js's `<Image>` component (automatic format negotiation, responsive `srcset`) or, at minimum, `loading="lazy"` on a plain `<img>`.                                                                                                            | `ProductCard.tsx` uses a plain `<img loading="lazy">`, not Next's `<Image>` — functional lazy-loading exists, but without Next's automatic format/size optimization. Worth a deliberate call on whether to migrate to `next/image`, given it needs a configured remote image loader once real seller-uploaded product images (not placeholders) are wired up.                                                                                                                                                                                                                     |
| **Lazy loading**                           | Below-the-fold sections (recommendations, related products) don't block first paint; route-level code-splitting is the default (automatic with Next.js App Router — nothing extra required as long as large, rarely-used components aren't imported eagerly at the top of a page). | Consistent with Next.js defaults; no evidence of anti-patterns (e.g. barrel-importing the entire `@nova/ui` package eagerly) found in the files reviewed.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Optimistic UI for common actions**       | Add-to-cart and wishlist actions update the UI before server confirmation — see [01-data-fetching-conventions.md](01-data-fetching-conventions.md)'s full worked pattern.                                                                                                          | **Not implemented** — cart and wishlist don't exist yet beyond `ModuleShell` placeholders ([00-app-map.md](00-app-map.md)). This is a named Vol 6 requirement with a proposed pattern already written down, ready for when those features are actually built.                                                                                                                                                                                                                                                                                                                     |
| **Offline / degraded-connectivity states** | A real fallback UI when the network is unavailable, not a blank screen or an unhandled fetch rejection.                                                                                                                                                                            | Real, partial implementation: `apps/web/src/app/offline/page.tsx` exists, using a real `useNetworkStatus` hook and the shared `EmptyState` component. **But** there's no service worker or PWA manifest — no `next-pwa` equivalent, no `manifest.json` found anywhere in `apps/web`. That means this offline page is reachable if a user navigates to it directly, but nothing currently detects a network drop _automatically_ and routes the user there, and there's no actual asset/data caching that would make "cached content is available" (the page's own copy) true yet. |

## Performance budget — concrete numbers

> **Proposed, not yet confirmed.** Vol 6, E3 establishes the _categories_ of performance requirement (image optimization, lazy loading, optimistic UI, offline states) but no specific numeric budget. `backend/docs/06-testing-strategy.md`'s sibling document (Vol 7, E2) already sets backend-facing SLOs (checkout p95 < 800ms, search p95 < 500ms) — proposed frontend-facing budget, chosen to be consistent with those and with the "mid-tier Android, variable connectivity" market framing repeated across Volumes 1 and 6:
>
> | Metric                                          | Budget                                                                                             |
> | ----------------------------------------------- | -------------------------------------------------------------------------------------------------- |
> | Largest Contentful Paint (LCP)                  | < 2.5s on a simulated Slow 4G / mid-tier Android CPU throttle (Lighthouse's default mobile preset) |
> | Total JS shipped per route (first load)         | < 200KB gzipped                                                                                    |
> | Time to Interactive on the product listing page | < 3.5s under the same throttle profile                                                             |
>
> These would be enforced the same way the backend enforces its SLOs — as an automated CI check (e.g. Lighthouse CI against a staging deploy) rather than a number someone remembers to check manually before release, consistent with Vol 7, Part C1's "every PR runs through the same pipeline" philosophy already established for the backend.

## Known risks in this area for Nova specifically

- **Storybook's a11y addon is installed but can't actually run** due to the unresolved build incompatibility — meaning the one piece of _automated_ accessibility verification currently wired into the repo is not functioning. Manual review is the only real check happening right now.
- **No offline caching actually exists**, despite a real offline fallback page — the page's own copy ("Cached content is available") is currently untrue. Worth fixing the copy or building the caching, not leaving the two mismatched.
- **`ModuleShell` placeholder pages (cart, wishlist) mean the specific Vol 6, E3 requirement — optimistic UI for exactly those two actions — has no real implementation to check against yet**, and it's easy for that requirement to get lost between "the doc says do it" and "the feature finally gets built" if nobody re-reads this doc at that point.
- **No systematic contrast audit has been run against the actual token pairings**, despite the tokens themselves having been carefully corrected for brand accuracy — visual correctness and contrast compliance are two different properties, and only the first has had focused attention so far.
